Methodology

How this dashboard is measured

Where every number on the dashboard comes from, how it is calculated, how much confidence it deserves, and what it does not cover. Every value is read from a public source or from the repositories themselves on each refresh; nothing is entered by hand except the list of repositories to track and the license policy.

1. Scope and refresh

The dashboard tracks the repositories listed in config/repos.json. Each repository is shown on two branches:

  • Development: the repository's dev_branch in the config, else the first branch matching branches.development. Repositories without one appear only under Main.
  • Main: the repository's default branch on GitHub.

Data is collected by the refresh workflow and published as data/coverage.json and data/stack.json. Refresh data on the dashboard opens that workflow; running it requires write access to this repository. Badges are live; every other figure reflects the last completed run, whose time is shown as Updated.

2. Code coverage

Source
Codecov's report for the branch. When Codecov has none, the coverage file saved by the latest CI workflow run on that branch.
Calculation
Covered lines divided by measured lines. Partially covered lines count as not covered.
Measured
The commit time of the commit the coverage belongs to, or the CI run time. A date more than 14 days old is shown in amber as stale.
No report
Nothing was uploaded for that branch. It does not mean 0%. The dashboard never runs tests itself.

3. Security workflow

The result of the latest completed run of the repository's security.yml on the branch, with the time it finished (Last run). No runs on this branch means the workflow does not run there; it is not a failure.

4. Releases

Versions are found from release branches (release-1.2.0), git tags (v1.2.0) and GitHub Releases, as configured under releases. v1.2.0 and 1.2.0 are one version; names that are not versions are ignored. A release branch is measured as it is now, with live badges; a tag or GitHub Release is measured at its tagged commit, so it shows fixed figures and the date of the last run.

5. Dependencies

What is listed
The dependencies each repository declares directly, read from a fresh clone of each branch by specfy/stack-analyser and the repository's own manifests: package.json, go.mod, requirements*.txt, pyproject.toml, Dockerfiles and compose files, GitHub workflows (including the actions that local actions use), and tools downloaded from GitHub Releases. Indirect dependencies from lockfiles are not listed.
Version
The version the manifest declares. When it declares a range (^5.0.0) and a lockfile is present (package-lock.json, uv.lock, poetry.lock), the installed version from the lockfile is shown and used for every lookup.
Group
Where the project declares the package: main, dev, test, optional, peer or a named group, as the repository names it. Docker images are runtime; GitHub Actions are ci.
Latest
Packages: the newest release on deps.dev. Actions: the latest GitHub Release. Images: the newest tag of the same shape in the image's registry (17 → 18, 25.7-alpine → 25.12-alpine). For a floating tag such as latest, the version it points to today is found by comparing image digests, and its newest version is compared with that.
Image kind
The first category Docker Hub files the image under, as Docker Hub writes it; otherwise the first GitHub topic of the image's source repository; otherwise Container.
Stars and archived
GitHub stars of the dependency's source repository (from deps.dev, else GitHub), or Docker Hub stars for an image with no known repository. A repository archived on GitHub is marked archived.

6. Licenses

Each license is read, in this order, from the first source that states one:

  1. Packages: deps.dev for the exact version; GitHub's license detection on the source repository when deps.dev reports a non-standard license; the wheel's own metadata for packages installed from a wheel file; PyPI's metadata.
  2. Images: the license file of the image's source repository at the release tag the image's version names (so redis:7, today 7.4.12, is read at Redis 7.4.12); the image's org.opencontainers.image.licenses label; the repository its source label names; the license of the image's own program found inside it.
  3. Actions: the license of the action's repository.

When GitHub cannot name a license file, its text is compared word by word with the official SPDX license texts; a name is given only for a clear match. A file holding several licenses is read section by section and joined with OR when it offers a choice. A license that is not on the SPDX list keeps the short name its own heading gives it (LicenseRef-RSALv2).

License risk classes each license against the Preferred (green), Not recommended (yellow) and Restricted use (red) lists in config/repos.json. For A OR B the better class counts; for A AND B, or several licenses listed together, the worse. A license on no list is Unclassified.

7. Vulnerabilities

A vulnerability is one published advisory about one flaw (for example CVE-2024-1234), naming the affected package, the affected versions, a severity and, where one exists, the version that fixes it. The Vulnerabilities tab lists each advisory once, with every place it was found.

Severity
The severity the advisory states, or its CVSS score banded as critical (9.0+), high (7.0–8.9), medium (4.0–6.9) and low. Advisories with neither are not rated.
Fixed in
For a package, the lowest version that fixes every fixable advisory. For an image, each fix belongs to a package inside it; a newer image tag usually includes them.
Not checked
Shown as nil with its reason: an unresolved ${VAR} tag, a private or locally built image, an unpinned version, or a failed lookup. A failed lookup is never shown as “None known”.

8. Confidence and limitations

No scanner is complete or free of false positives. Independent scanners commonly disagree by 10–30% on the same image. The table states how far each figure can be relied on.

FigureConfidenceWhy
Image identity and versionHighThe exact tag is scanned; the version behind a partial or floating tag is matched by image digest, not inferred from its name. A floating tag can move between the run and the time of reading.
Packages inside an imageHighRead from the image's own package database (dpkg, apk) and from build information compiled into Go and Java programs.
Image vulnerabilitiesMediumEvery advisory matching an installed version is reported, including ones the distribution marks as disputed, minor or “will not fix”. Counts are therefore likely higher than those of scanners that apply distribution status (Trivy, Grype). Whether the vulnerable code is reachable is not assessed.
Package vulnerabilities, with a lockfileHighChecked at the exact installed version against OSV.dev.
Package vulnerabilities, without a lockfileMediumChecked at the lowest version the range allows, so advisories already fixed in the installed version may be reported. Such rows say so.
GitHub Actions vulnerabilitiesMediumMatches are exact, but few actions have published advisories, so “None known” carries little weight.
SeverityMediumTaken from the advisory; many distribution advisories carry none (not rated).
Fixed version inside imagesMediumDerived from each advisory's affected ranges; operating-system version strings (epochs, revisions) are compared by their numbers.
LicensesHighRead from registries and license files. A license file is named from its text only on a clear match to the SPDX text; otherwise it is left unnamed rather than guessed.

Not covered: indirect (transitive) dependencies, private registries, runtime configuration, and whether a vulnerable function is actually called.

9. Reading the dashboard

nil and N/A
nil: the value exists but could not be obtained; the tooltip gives the reason. N/A: there is no such value (a local action has no releases).
Filters
Within one filter the selected values are combined with OR; separate filters with AND. Each option shows how many items it would leave. The repository filters at the top apply to every tab. Filters are kept in the address, so a link shares the view.
Excel
Each table's spreadsheet button downloads the rows it shows, with filters applied. Download all exports everything on both branches without filters.
