Where this comes from
  • Packages. specfy/stack-analyser reads the manifests (package.json, go.mod, requirements.txt, pyproject.toml, compose files, workflows) on each repository's development branch and default branch. These are direct dependencies, not the full lockfile tree.
  • Group. Where the project declares each package: package.json dependencies (main), devDependencies (dev), optional and peer; pyproject.toml [project] dependencies (main) and every named group in optional-dependencies, dependency-groups and Poetry groups, as the repository names them (tests/testing read as test, develop as dev); requirements.txt (main) and requirements-<name>.txt or requirements/<name>.txt (that name, e.g. dev, test, prod); go.mod direct requires (main) and tool lines. Docker images are runtime and GitHub Actions are ci. When the manifest gives a range such as ^5.0.0, the version the lockfile next to it installs (package-lock.json, uv.lock, poetry.lock) is shown and checked for vulnerabilities. Indirect packages from lockfiles are not listed.
  • License and latest. From deps.dev for npm, PyPI and Go. When the listed version is a range or unknown there, the license of the latest release is shown and marked latest.
  • Vulnerabilities. From OSV.dev, Google's open vulnerability database (GitHub advisories, PyPI, Go and others). It is a public API that needs no key or login, and only package names and versions are sent. A package is checked at the version listed here; for a range such as ^5.0.0 that is the lowest version the range allows, so the real installed version may be newer and already fixed. Fixed in is the one version that fixes every fixable advisory; advisories with no released fix are counted separately.
  • License risk. Each license is matched against the green, yellow and red lists under licenses in config/repos.json. For an expression A OR B the better class counts, for A AND B the worse (AND binds tighter, parentheses are respected). Several licenses listed together (MIT, Apache-2.0) are treated as all applying, so the worst counts. A license on no list, or one that cannot be read, is unclassified.
  • Filters. Within one filter the ticked values are OR-ed; different filters are AND-ed. Each option shows how many dependencies it would give. The address bar holds the filters, so a link shares the view.
  • GitHub Actions. From the GitHub API. A tag such as v4 is checked at the newest release it covers today (shown under the version, e.g. v4.3.0); a commit pin at the release tag on that commit. Latest is the action's latest release, license is the action repository's license, and vulnerabilities come from the GitHub Advisory Database (OSV holds these advisories but cannot match them to a version). Actions inside the repository (./.github/actions/...) are N/A.
  • Docker images. Latest is the newest tag of the same shape in the image's registry (17 → 18, 25.7-alpine → 25.12-alpine), asked anonymously; a floating tag such as latest has none (N/A). Vulnerabilities come from osv-scanner, which pulls the image and checks the operating-system packages and binaries inside it against OSV (nothing in the image is run). Fixes belong to packages inside the image, so Fixed in counts how many are fixable; a newer tag usually includes them. Private images, images built only locally and unresolved ${VAR} tags are not scanned (nil). License is N/A: an image holds many packages, each with its own license.
